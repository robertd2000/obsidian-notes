## 1. OpenIM

**GitHub:** https://github.com/openimsdk/open-im-server

### Стек
- Go
- gRPC / HTTP API
- Kafka
- Redis
- MySQL / MongoDB
- WebSocket

### Архитектура: на какие папки смотреть
- `internal/api/` — HTTP API layer
- `internal/rpc/` — внутренние gRPC-сервисы
- `internal/push/` — push notifications
- `internal/msgtransfer/` — обработка сообщений, Kafka consumers
- `internal/msggateway/` — WebSocket gateway
- `internal/user/`, `internal/friend/`, `internal/group/` — бизнес-домены
- `pkg/` — переиспользуемые пакеты
- `cmd/` — entrypoints сервисов

### Почему это хороший backend
Это реальный production IM backend:
- пользователи, группы, сообщения;
- auth/token;
- realtime delivery;
- Kafka как транспорт;
- Redis как кэш/состояния;
- разделение на API/RPC/push/transfer/gateway.

### Плюсы
- реальный бизнес-подобный backend;
- есть broker, cache, auth;
- хорошая база для изучения Go microservices;
- много async/event-driven логики;
- много сервисов и внутренних API.

### Минусы
- местами сложная документация;
- проект быстро развивается, структура может меняться;
- часть кода сильно привязана к IM-домену;
- production deploy не самый простой.

# Важное замечание про FastAPI

Честно: **готовых production FastAPI microservices с Kafka, Redis, auth и красивой декомпозицией на GitHub мало**.

Обычно FastAPI встречается как:
- один API-сервис внутри большой системы;
- template для старта;
- internal service;
- ML/AI backend.

Поэтому для FastAPI лучшая стратегия:
1. Взять **full-stack-fastapi-template**.
2. Посмотреть **Prefect** и **Dispatch** как реальные FastAPI backend.
3. Изучить event-driven patterns из **Sentry** / **PostHog**.
4. Перенести эти паттерны в свой FastAPI microservice design.

# Что именно смотреть в коде, чтобы учиться микросервисам

В каждом проекте обращай внимание не на README, а на:

## 1. Как разрезаны сервисы
Папки вида:
```text
users/
orders/
payments/
inventory/
notifications/
gateway/
```

Ищи:
- отдельный сервис под домен;
- свой API;
- свою БД или schema;
- свои модели.

---

## 2. Как сервисы общаются
Ищи:
- REST clients;
- gRPC clients;
- message producers;
- event consumers;
- protobuf/OpenAPI definitions.

Хорошие признаки:
- контракты вынесены отдельно;
- есть versioning;
- есть retry/timeout;
- есть error mapping.

---

## 3. Где broker
Ищи папки:
```text
consumers/
producers/
events/
subscribers/
handlers/
kafka/
rabbitmq/
nats/
```

Смотри:
- как публикуется событие;
- как обрабатывается ошибка;
- есть ли DLQ;
- есть ли idempotency key;
- как подтверждается сообщение.

---

## 4. Где cache
Ищи:
```text
cache/
redis/
invalidation/
```

Смотри:
- cache-aside или write-through;
- TTL;
- invalidation;
- race conditions;
- serialization.

---

## 5. Где auth
Ищи:
```text
auth/
security/
middleware/
jwt/
oauth/
rbac/
permissions/
```

Смотри:
- token validation;
- user context;
- role checks;
- service-to-service auth;
- permission model.

# Итоговая рекомендация

Если хочешь **максимально быстро получить пользу**, изучай в таком порядке:

## Шаг 1: База FastAPI / Spring / Go
- FastAPI: `full-stack-fastapi-template`
- Spring: `Spring PetClinic Microservices`
- Go: `Online Boutique`

## Шаг 2: Реальные backend systems
- Go: `OpenIM`, `Harbor`
- Python: `Prefect`, `Sentry`
- Java: `FTGO Application`, `Spring Cloud Data Flow`
- Rust: `Hyperswitch`

## Шаг 3: Продвинутая архитектура
- broker patterns: Kafka в Sentry/PostHog/FTGO/OpenIM
- caching: Redis в OpenIM/Harbor/Sentry/PostHog
- auth: Bank of Anthos, Harbor, Hyperswitch, Sentry
- service boundaries: FTGO, Bank of Anthos, Online Boutique
