Ок, если **production не обязателен**, тогда можно взять максимально близкие проекты: учебные бизнес-микросервисы, event-driven примеры, магазины/банки/заказы, Kafka/RabbitMQ, outbox, sagas, метрики, логи.

Ниже — **20 проектов**, без чистых фреймворков.  
Я буду помечать:

- **Kafka** — есть ли Kafka / другой брокер;
- **Outbox** — есть ли transactional outbox / event publishing из БД;
- **DLQ** — есть ли dead letter queue явно;
- **Metrics/Logs** — есть ли observability.

# 1. FTGO Application

**GitHub:** https://github.com/microservices-patterns/ftgo-application

## Домен
Доставка еды:
- заказы;
- рестораны;
- кухня;
- доставка;
- пользователи.

## Стек
- Java
- Spring Boot
- Kafka
- MySQL
- Eventuate Tram
- Docker

## Архитектура: что смотреть
```text
ftgo-order-service/
ftgo-kitchen-service/
ftgo-restaurant-service/
ftgo-delivery-service/
ftgo-consumer-service/
ftgo-api-gateway/
ftgo-common/
ftgo-eventuate/
```

## Что там есть
- Kafka: ✅
- Outbox: ✅ через Eventuate Tram
- Saga: ✅
- DLQ: ⚠️ бедно, нужно докручивать
- Metrics/Logs: ⚠️ базовые

## Плюсы
- один из лучших примеров event-driven микросервисов;
- бизнес-домен;
- Kafka + saga + outbox;
- хорошо видны границы сервисов.

## Минусы
- учебный проект;
- местами устаревшие зависимости;
- мало production observability;
- DLQ/retry почти не раскрыты.

# Важное замечание про DLQ

В большинстве таких репозиториев **DLQ не реализован явно**, потому что это уже эксплуатационная часть. Обычно DLQ делается отдельно через:

- Kafka error topic;
- retry topic;
- dead-letter topic;
- consumer retry policy;
- idempotency key;
- correlation id;
- metrics consumer failures.

Поэтому если в проекте нет DLQ — это нормально для sample.  
Ты можешь взять условный FTGO/Eventuate и добавить:

```text
orders.events
orders.events.retry
orders.events.dlq
```

и это уже будет ближе к production-паттерну.
